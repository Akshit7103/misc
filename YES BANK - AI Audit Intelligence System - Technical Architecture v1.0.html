1How to read this document

This document answers three of the Bank’s asks in one place: the technical architecture document and high-level architecture diagram required under §3.2 (Documentation and Expected Deliverables), and “Architecture of Technology & Product RoadMap”, which is point 1 of the nine-point techno-commercial submission under §6.

Two layers, always labelled

A reference implementation of this platform already exists and runs. It is not a slide-ware mock-up: it ingests data through real connectors, compiles and executes 78 controls against frozen evidence, and reproduces a run byte-for-byte on demand. It is also, today, a single-process reference environment.

The Bank’s non-functional targets — 5,000+ concurrent users, 99.9% availability, DR RPO of zero and RTO of one hour — describe a production deployment, not a reference environment. Presenting one as the other would be misleading, and would not survive technical evaluation. Every architectural statement in this document is therefore tagged:

As-built Implemented and demonstrable today in the reference environment. Can be shown working in the prototype demonstration the RFI requests.
As-proposed Part of the production architecture for YES BANK. Designed, sized and costed, but delivered during implementation — not demonstrable today.

3Architecture principles

Seven principles govern the design. Each is stated with the mechanism that enforces it, because a principle without a mechanism is a preference.

1 · Evidence is immutable and content-addressed

A control never runs against a live source system. It runs against a frozen snapshot whose identity is the hash of its contents.

Mechanism: each pull writes Parquet files and a manifest of per-table SHA-256 digests; the snapshot id is the SHA-256 of that manifest plus the source key. Re-verification re-hashes every file. Altering one byte of evidence changes the id and is detected.

2 · Controls are configuration, not code

A control is authored as a row in a workbook and validated against a published schema. Adding or amending a control requires no release.

Mechanism: twelve declarative rule types compile to a SQL predicate. The compiler never raises on an author’s mistake — it returns the control as unexecutable with the reason, because a control that silently matches nothing is the worst failure mode in an audit system.

3 · AI reasons; code decides

Language models draft, explain and summarise. Every number that reaches a workpaper is computed by deterministic code.

Mechanism: model output is a proposal requiring human acceptance; the analytics path never calls a model. A generated control is compiled, validated and previewed against real data before it can be saved.

4 · The engine proposes; the auditor concludes

The system reports exceptions, populations and rates. It does not conclude that a control is ineffective — that judgement is the auditor’s and is recorded as theirs.

Mechanism: a run yields a proposed conclusion and never returns “Ineffective”; where controls could not be executed the run is marked inconclusive rather than clean.

5 · Separation of duties is enforced, not documented

Maker and checker are different people at every gate that matters.

Mechanism: the platform rejects self-approval of a control, self-review of a finding, verification of an action by its owner or by whoever closed it, self-approval of a deadline extension, and promotion of a model by the person who trained it.

6 · Everything is on the record and tamper-evident

Every state change is written to an append-only ledger; nothing updates or deletes a ledger row.

Mechanism: each entry carries the hash of its predecessor, so any alteration breaks the chain from that point forward and is located by re-computation. The chain head is independently verifiable.

7 · Data stays where the Bank puts it

No audit data leaves the Bank’s environment, including to an AI provider.

Mechanism: the inference layer accepts only loopback and private-host endpoints and refuses any non-local URL; an explicit configuration guard blocks external providers. Data residency is a property of the code, not of a policy statement.

4Solution context

The platform sits between the Bank’s systems of record and its audit function. It reads; it does not write back. No connector in the architecture has a write path to a source system, which removes an entire class of operational risk from the deployment conversation and simplifies the Bank’s change-approval process for connecting it.

5Logical architecture

The system is layered, and dependencies point one way only. No domain module imports the API layer; no data module imports a surface. This is what allows the control engine to be tested without a web server, and the ingestion pipeline to be exercised without a database — and it is why 649 automated tests can run in under a minute.

6Data architecture and evidence

The canonical model, and why it exists

A control in this platform never names a core-banking table. It names a canonical entity. Dormant_Reactivation_No_Approval is written against account, not against a physical table in Finacle or a view in the Data Warehouse.

This is the single most consequential design decision in the architecture, and it directly answers the RFI’s requirement for a prototype demonstrating integration “via YES BANK Data Warehouse, or direct connectivity to source applications”. Because controls bind to the canonical contract rather than to a physical schema, the same 78 controls run unchanged whether the Bank routes them through the Data Warehouse or connects them directly to core banking. Changing the route is a connector configuration change; it is not a re-write of the control library.

The eleven canonical entities are customer, account, transaction, loan, journal_entry, employee, entitlement, vendor, vendor_payment, kyc_document and aml_alert. Each declares a primary key, typed columns with required flags, and entity dimensions — branch, region, segment, product — carried from day one so that branch and regional analysis needs no retrofit.

The evidence pipeline

Retention, lineage and reconciliation

  • Lineage As-built — every exception carries its run id; every run carries its snapshot id and the exact SQL executed; every snapshot carries per-table content hashes and row counts. An auditor can move from a number in a workpaper to the specific frozen dataset it came from without leaving the system.
  • Reconciliation reports As-built — pull-level row counts, rejected-row detail and per-table content hashes support source-to-platform reconciliation. §3.2 asks for reconciliation reports; the data to produce them is captured at ingestion.
  • Retention and archival As-proposed — configurable retention with WORM archival of snapshots and ledger segments. Snapshots are already immutable and content-addressed, which is the hard half; the policy engine and archival scheduling are implementation-phase work.

7Control architecture

Controls are the Bank’s intellectual property, not the vendor’s. The architecture reflects that: a control is a validated configuration object that the Bank can author, review, approve and version without a release, and without the vendor.

The twelve control types

TypeTests
ComparisonA column against a threshold, a value or another column, typed from the canonical contract rather than from the literal
Is_Null / Not_NullPresence or absence of a value, treating a blank string and a null identically
Value_In_SetMembership in a permitted list; a blank counts as outside the set and is flagged
Date_OrderChronological relationship between two dates — a document verified before it was received
Date_DiffElapsed days between two dates against a limit — TAT and ageing controls
Date_AgeAge of a record relative to the snapshot date — dormancy, staleness, expiry
DuplicateRepeated key combinations, with blank keys excluded because three missing invoice numbers are a completeness issue, not a duplicate-payment issue
Group_AggregateCount, sum, min or max within a group against a limit — splitting, structuring, concentration
Group_ShareConcentration of a group as a share of the whole — vendor and channel dependence
Matrix_LookupAuthority matrices: the level required for an amount against the level actually held. A missing amount takes the highest band, so an unrecorded sanction fails open
ExpressionFree-form predicate, restricted to canonical columns and an allow-list of deterministic SQL functions; non-deterministic functions are refused so a control cannot return different rows on re-run

Reproducibility

As-built Re-executing a completed run against the same snapshot produces an identical results hash, and the verification replay deliberately does not write a second copy of the exceptions. The Bank can therefore prove to a regulator that a conclusion reached six months ago is reproducible today from the archived evidence, using the control version that was in force at the time.

8AI and ML architecture

Two distinct capabilities are often conflated in RFI responses. This architecture keeps them separate because their governance requirements are different.

Generative AI

As-built Inference runs on-premise. The provider layer parses every configured endpoint and refuses any URL that is not a loopback or private host, with a separate configuration guard that must be explicitly set to permit an external provider. A scheme-less host string that could be read as a remote endpoint is rejected rather than accepted by default. In the reference environment the model is served locally; in production the Bank chooses the model and the hosting node.

Generative capabilities in scope: drafting a control from a natural-language description (compiled, validated and previewed against real data before it can be saved), drafting findings and multi-level report narratives from recorded evidence, drafting auditee queries, and the policy assistant. The assistant answers strictly from an indexed corpus with per-document role-based access enforced at retrieval time, cites the document, version and page for every claim, surfaces contradictions where two documents disagree, and returns “I don’t know” rather than speculating when the corpus does not contain the answer.

Machine learning

As-built Two models, both governed by the registry shown above:

  • Exception triage — a gradient-boosted classifier over 17 engineered features predicting the probability that an exception will be confirmed on review, blended with a documented heuristic so the score never becomes an unexplainable number. Trained on the audit function’s own dispositions. In the reference environment it achieves a held-out AUC of 0.785, with precision and recall reported alongside; SHAP contributions accompany every score.
  • Anomaly detection — an isolation forest over the same feature space, unsupervised so it needs no labelling history to be useful on day one.

Every score the platform acts on is written as an immutable decision record carrying the model key, version, inputs and reasoning — so the question “why did the model say that, on that day, with that model?” is answerable at review time.

As-proposed Drift, bias and accuracy monitoring with scheduled re-training proposals. The registry, versioning, approval and rollback machinery this depends on is already in place; the monitoring loop is implementation-phase work.

9Security architecture

This section responds to §3.2 (Security & Compliance) and §5.5 (Security Features). The clause-by-clause response is in the Technical & NFR Response Matrix; what follows is the architecture behind it.

Identity and access

ControlStatusDesign
Role-based access controlAs-built Five roles — administrator, audit manager, auditor, reviewer, auditee. Every one of the 117 operations carries an explicit role dependency; there is no unguarded endpoint other than login and health.
Segregation of dutiesAs-built Enforced in code at six gates: control approval, checklist approval, finding QA, action verification, extension approval, model promotion.
Password storageAs-built PBKDF2-HMAC-SHA256 at 600,000 iterations with a per-user salt. Login performs equivalent work for a non-existent user, so response time does not disclose which usernames are valid.
Session managementAs-built Signed bearer token, 12-hour lifetime, HttpOnly and SameSite=Strict cookie with the Secure attribute configurable for TLS deployment.
Separate user-management moduleAs-built Administration surface for provisioning, role assignment, activation and de-activation, with a guard preventing removal of the last active administrator.
AD / LDAP integrationAs-proposed §3.2 requires AD login. Delivered as a pluggable authentication provider — LDAP bind or SAML/OIDC against the Bank’s identity provider, with group-to-role mapping. The authorisation model is unchanged; only the authentication step is replaced.
Multi-factor authenticationAs-proposed Delegated to the Bank’s identity provider once AD/SSO is in place, which is the Bank’s preferred pattern and avoids a second MFA estate.
User dormancyAs-proposed Automatic de-activation after a configurable idle period. Last-login is already recorded per user.

Data protection

  • In transit As-proposed — TLS 1.2+ terminating at the Bank’s load balancer or WAF, with mutual TLS between application and data zones. §5.5 requires encryption in transit including between the application and interfacing systems; connector configurations support TLS-secured endpoints for SQL, SFTP and REST.
  • At rest As-proposed — transparent data encryption at the database tier and encrypted volumes for the snapshot store. Handled at the platform tier rather than in application code, which is the pattern the Bank’s existing estate already operates and audits.
  • Secrets As-built — connector credentials are treated as write-only. They are masked in every API response and in the audit ledger, and a client that echoes a masked value back on edit does not overwrite the stored secret. This matters because the ledger is immutable: a credential written there could never be redacted.
  • PII Partial — the canonical model carries identity documents in masked form by design. Field-level masking policies by role, and DPDP-aligned subject-rights handling, are implementation-phase work.

Application security

The platform is developed against OWASP guidance, and the reference implementation has been through a full internal security review whose findings were remediated before this submission. Parameterised queries and an allow-list of canonical identifiers throughout; uploads are extension-restricted, size-capped and streamed, with the destination path confined to the upload directory; every list endpoint is bounded at both ends so pagination cannot be defeated; error responses do not leak internal state. Independent VAPT and source code review are scheduled as pre-go-live activities and their reports form part of the implementation deliverables (§5.5, §6).

10Integration architecture

§3.2 requires APIs for integration with the Data Warehouse, core banking, CRM, Pentana and other source applications. The platform integrates in one of two directions, and the Bank can mix them per source.

ConnectorStatusUse and configuration
SQLAs-built Direct read against the Data Warehouse or a core-banking replica over a SQLAlchemy-supported driver — Oracle, PostgreSQL, SQL Server, MySQL. Per-table query or view mapping. This is the recommended primary route for the Bank’s DW.
SFTPAs-built Scheduled collection of extract files from a landing zone, key- or password-authenticated. The pattern most core-banking teams prefer because it requires no inbound access to the source.
FileAs-built A mounted drop directory, reads confined to that directory so a configuration value cannot traverse the host filesystem. Used for nightly extracts and for one-off audit data requests.
RESTAs-built For source applications exposing an API — CRM, Pentana, V-CIP platforms. Bearer or basic authentication, offset or cursor pagination, with paging that stops only on a genuinely empty page so a server-side page-size cap cannot silently truncate the population.

Mapping, drift and failure

Each source declares a mapping from its physical columns to canonical columns. At ingestion, values are coerced to the declared canonical types; a value that cannot be coerced rejects that row with a recorded reason and column, and the pull continues. Absent optional values are recorded as null rather than treated as failures. Schema drift — a column that disappears or changes type between pulls — is detected and reported against the pull rather than discovered later as a control that quietly stopped finding anything.

Outbound and platform APIs

As-built All 117 operations are documented in an OpenAPI specification served by the platform, covering ingestion, controls, runs, exceptions, sampling, workpapers, the audit lifecycle, workflow, AI services and administration. This allows the Bank to drive the platform from an orchestration tool, feed dashboards into an enterprise BI layer, or push findings into an existing GRC system. The Integration & API Documentation deliverable is generated from this specification, so it cannot drift from the implementation.

11Deployment architecture

This is the section where the two layers differ most, so the difference is drawn explicitly rather than described.

Data centre and disaster recovery

Scaling and sizing

Target (§3.2)Architectural response
5,000+ concurrent usersStateless application tier scaled horizontally behind the load balancer; sessions are bearer tokens, so no sticky sessions and no shared session store. Read-heavy dashboard traffic served from the relational tier with a read replica.
Response time < 2 secondsInteractive requests are served from the relational store. Analytical work — control execution over millions of rows — runs against columnar Parquet through a vectorised engine and is asynchronous by design: a run is submitted and tracked, not waited on.
High-volume loads, large branch networksIngestion is per-source and parallelisable; snapshots are immutable so readers never contend with writers. Controls execute against columnar storage with predicate push-down.
Multi-entity, multi-process parallel executionRuns are independent units keyed by pack and snapshot; several engagements execute concurrently without interaction, which is a consequence of pinning every run to frozen evidence.
Horizontal scaling for peak audit cyclesApplication nodes added and removed without state migration. Peak audit periods are handled by scaling the tier rather than by capacity held idle year-round.
75% utilisation ceiling (§5.3)Sizing in the BOQ is calculated to hold CPU, memory, storage and network below 75% at both DC and DR under the modelled peak.

Cloud portability

§5.3 requires that the solution be capable of being shifted from on-premises to the Bank’s cloud provider. The architecture holds no on-premises assumption: the application tier is a stateless process, the relational store is accessed through a database abstraction supporting Oracle, PostgreSQL, SQL Server and MySQL, and the snapshot store is object storage. The same build deploys to on-premises, private cloud or public cloud; inference remains inside whichever boundary the Bank designates, and the residency guard travels with the application.

Environments

§3.2 requires separate UAT and DR environments and separate application and database servers. Four environments are proposed — Development, UAT, Production and DR — with separate application and database hosts in each of Production and DR. Because a snapshot is content-addressed, a dataset promoted from UAT to Production is provably the same dataset, which makes UAT sign-off meaningful rather than indicative.

Why no front-end framework

This is a deliberate architectural choice with a security consequence the Bank’s application-security team will recognise: there is no build pipeline, no transitive npm dependency tree, and no gap between the code that was reviewed and the code that is served. Front-end supply-chain risk is removed rather than managed.

15Assumptions and prerequisites

Prerequisites from YES BANK (§6, point 9)

  • Hardware, operating system and Oracle Database licences per §5.3, sized to the BOQ submitted with the commercial response.
  • Network connectivity from the application zone to each in-scope source system, and a landing zone where SFTP or file collection is the agreed route.
  • Data dictionaries and sample extracts for each source, to complete the physical-to-canonical mapping.
  • Identity provider integration details for AD/SSO, and the group-to-role mapping the Bank wishes to apply.
  • Load balancer, WAF, SIEM and DAM integration endpoints and the applicable configuration standards.
  • The Bank’s IT and IS security policies, encryption standards and password policy, referenced in §5.1 as shared with the selected bidder.
  • Nominated business owners per initiative for control-library sign-off, and UAT participants.
  • DC and DR facilities with the network capacity to support synchronous database replication.

Assumptions

  • Source systems are read-only from the platform’s perspective; no write-back is in scope.
  • The Data Warehouse is the primary integration route where a required entity is available there, with direct source connectivity used by exception.
  • Control logic is the Bank’s to own and amend; Protiviti provides the initial library and the authoring capability.
  • Language model selection and hosting are agreed jointly, and inference remains within the Bank’s boundary in all cases.
  • Availability figures are for the application; the end-to-end figure depends on the Bank’s infrastructure and network SLAs.

Exclusions

  • Provision of hardware, operating system and Oracle licences (§5.3 places these with the Bank).
  • Remediation of data quality within source systems; the platform reports it rather than corrects it.
  • Changes to source applications to expose data not currently available.
  • Third-party licence costs for systems the platform integrates with.
What we would show at demonstration

An end-to-end run in the reference environment: connect a source and pull it, watch the data become a content-addressed snapshot, execute a control pack against it, triage the exceptions, select a statistical sample, raise a finding through QA into a management action, generate the workpaper, then verify the ledger chain and re-run the whole thing to prove the same evidence produces the same answer. Approximately 40 minutes, with nothing pre-recorded.
